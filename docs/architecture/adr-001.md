# ADR (Architecture Decision Record) 001 — Arquitetura static-first com Astro

- Status: Aceita
- Data: 2026-08-26

## Contexto

A Issue 001 apresenta conteúdo editorial, catálogos musicais, programas,
players e informações de contato. Os arquivos de sets, Maremoto Sessions e
Te convido para um Date recebem atualizações periódicas conforme novas
edições são transmitidas e suas gravações são disponibilizadas.

Atualmente, essas atualizações podem ser adicionadas ao repositório e
publicadas por meio de um novo build. O projeto ainda não exige edição em
tempo real, autenticação, persistência dinâmica ou processamento no
servidor.

O projeto também deve oferecer boa performance, HTML semântico,
acessibilidade e funcionamento útil sem JavaScript.

## Decisão

Usar Astro para gerar a homepage como HTML estático durante o build.

Componentes Astro são o padrão para layout, conteúdo e apresentação.
JavaScript no cliente é permitido somente quando uma interação real não
pode ser atendida por HTML e CSS.

Conteúdo e links permanecem disponíveis no HTML inicial. Recursos externos
mais pesados, como players incorporados, são carregados somente após uma
ação explícita.

Backend, API e banco de dados não fazem parte da arquitetura atual porque
ainda não existe uma necessidade de persistência ou processamento
dinâmico.

## Alternativas consideradas

### Aplicação React totalmente client-side

Permitiria construir toda a interface com uma única tecnologia, mas
enviaria JavaScript para conteúdo que pode ser representado por HTML
estático. Também aumentaria o custo inicial de carregamento e tornaria o
conteúdo mais dependente da execução no cliente.

### Renderização no servidor

Permitiria gerar respostas dinamicamente a cada requisição, mas exigiria
infraestrutura de execução sem que o conteúdo atual precise dela.

### Backend separado desde o início

Criaria espaço para persistência e regras de negócio futuras, porém
introduziria implantação, observabilidade e manutenção antes da existência
de um domínio dinâmico que justificasse esses custos.

## Consequências

### Positivas

- A maior parte da página é entregue como HTML estático.
- Conteúdo editorial permanece acessível sem JavaScript.
- A superfície operacional e a infraestrutura são reduzidas.
- Astro permite adicionar ilhas interativas sem transformar todo o site em
  uma aplicação client-side.
- Erros de conteúdo podem ser identificados durante o build.

### Negativas

- Funcionalidades dinâmicas futuras podem exigir API, persistência ou
  renderização no servidor.
- Interações de cliente precisam ser tratadas como exceções arquiteturais.
- Cada novo set ou episódio exige alteração no repositório, novo build e
  deploy.

## Progressive enhancement

A experiência principal deve existir em HTML antes da execução de
JavaScript. A interatividade pode melhorar essa experiência, mas não deve
ser necessária para acessar textos, arquivos ou links externos.

## Quando reavaliar

Esta decisão deve ser reavaliada quando o produto exigir:

- conteúdo que precise ser publicado imediatamente ou sem alteração no
  repositório;
- autenticação ou conteúdo personalizado;
- solicitações de booking persistidas;
- agenda administrável;
- processamento no servidor;
- dados compartilhados por múltiplos clientes.
