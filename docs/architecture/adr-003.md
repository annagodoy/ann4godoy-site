# ADR (Architecture Decision Record) 003 — Hidratação seletiva dos players com React

- Status: Aceita
- Data: 2026-08-26

## Contexto

A maior parte da Issue 001 é conteúdo editorial estático. Os players são a
única área que precisa manter estado no cliente para selecionar um registro,
comunicar a seleção e trocar o embed entre SoundCloud e YouTube.

Carregar todos os iframes durante a abertura da página criaria requisições
para serviços externos antes de qualquer intenção de reprodução. Também
aumentaria o custo inicial da página e anteciparia o contato do navegador
com terceiros.

O catálogo e seus links externos precisam continuar úteis quando JavaScript
estiver indisponível.

## Decisão

Usar React somente no componente interativo `SetPlayer`.

Uma ilha é uma região interativa isolada dentro de uma página
majoritariamente estática. A hidratação ocorre quando o JavaScript do React
se conecta ao HTML dessa ilha e ativa seu estado e seus eventos.

Cada instância é renderizada como uma ilha Astro com `client:visible`.
A hidratação começa quando a ilha se aproxima da área visível, em vez de
ocorrer imediatamente durante a abertura da página.

O estado inicial não possui seleção e não renderiza iframe. Um embed do
SoundCloud ou YouTube é criado somente após a pessoa selecionar um item.

O `SetPlayer` recebe dados serializáveis preparados pela página e delega a
construção dos embeds aos adaptadores `SoundCloudPlayer` e `YouTubePlayer`.

Os catálogos estáticos preservam links diretos para as plataformas como
caminho independente do player.

## Alternativas consideradas

### Iframes renderizados durante o build

Seria a implementação mais simples, mas carregaria recursos externos antes
da interação, aumentaria o custo inicial e reduziria o controle sobre
privacidade e desempenho.

### React em toda a homepage

Ofereceria uma única tecnologia para toda a interface, mas hidrataria
conteúdo editorial que não precisa de estado ou eventos no cliente.

### JavaScript nativo

Poderia implementar a seleção com menos dependências e um bundle menor.
Entretanto, React foi adotado de forma deliberada como experimento de estudo
e mantém estado, renderização condicional e acessibilidade concentrados em
um componente isolado.

### Páginas ou links sem player incorporado

Manteriam o site completamente estático e seriam a solução de menor custo,
mas removeriam a experiência de reprodução dentro do arquivo editorial.

## Consequências

### Positivas

- React fica restrito às áreas que precisam de estado.
- Nenhum iframe externo existe no HTML inicial.
- O embed é carregado somente após seleção explícita.
- O mesmo player pode ser reutilizado em diferentes arquivos.
- Links estáticos mantêm um caminho funcional sem JavaScript.
- A integração com cada plataforma fica isolada em um adaptador.

### Negativas

- React e seu runtime são enviados ao navegador.
- Cada ilha precisa ser hidratada e manter seu próprio estado.
- Astro e React coexistem no mesmo projeto, aumentando o conjunto de
  conceitos necessários para manutenção.
- A disponibilidade dos embeds depende de serviços externos.
- `client:visible` posterga a hidratação, mas não elimina o download de
  JavaScript quando a seção se torna visível.

## Privacidade e performance

A ausência de iframe inicial evita requisições aos provedores de mídia
antes da seleção. Depois da escolha, o provedor pode realizar suas próprias
requisições e definir cookies conforme suas políticas.

O YouTube utiliza o domínio `youtube-nocookie.com`. O SoundCloud é carregado
somente após a escolha de um conteúdo hospedado nessa plataforma.

## Quando reavaliar

Esta decisão deve ser reavaliada quando:

- o bundle React se tornar desproporcional à interação oferecida;
- o player precisar compartilhar estado entre páginas ou seções;
- novos provedores tornarem os adaptadores difíceis de manter;
- requisitos de consentimento impedirem embeds diretos;
- uma solução nativa oferecer simplicidade suficiente;
- a experiência passar a exigir uma API oficial dos provedores.
