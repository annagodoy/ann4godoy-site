# ADR (Architecture Decision Record) 002 — Conteúdo local validado no build

- Status: Aceita
- Data: 2026-08-26

## Contexto

O site mantém três conjuntos de conteúdo musical:

- catálogo geral de sets;
- episódios de Maremoto Sessions;
- episódios de Te convido para um Date.

Esses registros recebem atualizações periódicas e possuem campos
estruturados, como identificador, data, plataforma, URL e identificador do
provedor.

O conteúdo precisa permanecer versionado, revisável e consistente, mas
ainda não exige edição por pessoas sem acesso ao repositório ou publicação
independente de um deploy.

## Decisão

Armazenar os registros em arquivos JSON dentro de `src/data/` e carregá-los
por meio de Astro Content Collections.

Definir schemas em `src/content.config.ts` para validar os registros durante
o build. Dados inválidos devem interromper a geração do site.

Datas são convertidas para `Date` pelo schema. A ordenação é responsabilidade
da consulta realizada pela página, sem mutar o resultado original da
coleção.

Cada programa possui uma coleção própria quando seu modelo editorial difere
do catálogo geral.

## Alternativas consideradas

### Conteúdo diretamente em `index.astro`

Seria suficiente para poucos registros, mas misturaria dados, consulta e
apresentação. Também dificultaria revisão, validação e crescimento dos
arquivos.

### JSON importado sem Content Collections

Manteria os dados separados da interface, mas não forneceria o mesmo
contrato de validação integrado ao build nem tipos derivados da coleção.

### CMS externo

Permitiria edição fora do repositório e fluxos editoriais mais completos,
mas adicionaria serviço externo, autenticação, modelagem remota e
dependência de rede sem necessidade atual.

### API e banco de dados

Permitiriam consultas e atualizações dinâmicas, porém exigiriam backend,
persistência, deploy e operação antes da existência de regras de negócio
que justifiquem esses custos.

## Consequências

### Positivas

- O conteúdo permanece versionado junto ao código.
- Pull requests e histórico do Git registram as alterações editoriais.
- Schemas detectam dados ausentes ou inválidos durante o build.
- Componentes recebem entradas tipadas.
- Cada programa pode evoluir seu próprio contrato de conteúdo.

### Negativas

- Toda atualização exige alteração no repositório e novo build.
- Pessoas editoras precisam conhecer o formato JSON e o fluxo do Git.
- Não existe interface de administração ou preview editorial independente.
- Relações e consultas complexas seriam limitadas pelos arquivos locais.
- Algumas validações semelhantes podem ser repetidas entre coleções.

## Quando reavaliar

Esta decisão deve ser reavaliada quando:

- pessoas não técnicas precisarem publicar conteúdo;
- o volume ou a frequência tornarem o fluxo via Git inadequado;
- for necessário agendar ou revisar publicações;
- os registros exigirem relações ou consultas complexas;
- múltiplos clientes precisarem consumir os mesmos dados;
- conteúdo precisar ser atualizado sem novo deploy.
