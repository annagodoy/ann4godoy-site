# ADR (Architecture Decision Record) 004 — Deploy estático no Cloudflare Workers

- Status: Aceita
- Data: 2026-09-03

## Contexto

O site é gerado pelo Astro como um conjunto de arquivos estáticos no diretório `dist/`.

O projeto precisava de uma URL pública gratuita, HTTPS e um processo de deploy automático conectado à branch `main`, sem introduzir renderização no servidor ou um backend.

## Decisão

Usar Cloudflare Workers Static Assets para hospedar e distribuir os arquivos gerados pelo Astro.

A configuração do Wrangler aponta somente para o diretório `dist/`:

```json
{
  "assets": {
    "directory": "./dist"
  }
}
```

O deploy contínuo é realizado pelo Cloudflare Workers Builds, conectado ao repositório GitHub.

Antes de cada publicação, o ambiente remoto executa:

```sh
npm run check && npm run build
```

Após o build, os arquivos são publicados com:

```sh
npx wrangler deploy
```

A versão pública utiliza temporariamente a URL gratuita:

<https://ann4godoy-site.annabfgodoy.workers.dev>

## Por que o adapter Cloudflare não foi usado

O projeto utiliza o modo estático padrão do Astro e não possui rotas renderizadas no servidor, middleware, funções ou backend.

O pacote `@astrojs/cloudflare` seria necessário para recursos executados no runtime do Cloudflare. Como o site entrega somente arquivos estáticos, adicionar o adapter aumentaria a complexidade sem benefício para o cenário atual.

## Alternativas consideradas

### GitHub Pages

Permite hospedagem gratuita diretamente pelo GitHub.

Não foi escolhido porque a URL do projeto normalmente teria o subdiretório `/ann4godoy-site/`, o que poderia exigir adaptações na configuração de caminhos do site.

### Cloudflare Pages

Também permite publicação de sites estáticos.

Cloudflare Workers Static Assets foi escolhido por ser a solução recomendada atualmente pela plataforma para novos projetos e permitir evolução futura dentro do ecossistema Workers.

### Vercel ou Netlify

Oferecem integração simples com repositórios e deploy automático.

Não foram escolhidos porque não apresentavam uma vantagem necessária para o projeto nesta fase e adicionariam outro provedor à arquitetura.

### AWS S3 e CloudFront

Oferecem hospedagem estática e distribuição por CDN.

Essa alternativa poderá ser útil futuramente como exercício de infraestrutura, mas possui uma configuração operacional e de custos maior do que o necessário para a primeira publicação.

### Deploy manual com Wrangler

O site poderia ser publicado diretamente pela máquina de desenvolvimento.

Foi escolhido o deploy conectado ao GitHub para evitar que a publicação dependesse de uma operação manual local.

## Consequências

### Positivas

- URL pública gratuita com HTTPS;
- deploy automático a partir da branch `main`;
- distribuição global dos assets estáticos;
- suporte futuro a domínio próprio;
- preservação da arquitetura static-first;
- possibilidade de builds de preview para outras branches.

### Negativas

- dependência da plataforma Cloudflare;
- CI e CD são executados em plataformas diferentes;
- parte das verificações é repetida no GitHub Actions e no Cloudflare;
- a URL `workers.dev` está vinculada à conta Cloudflare;
- pushes na `main` podem publicar uma nova versão automaticamente;
- o Wrangler apresenta aviso de compatibilidade no macOS 12.6, embora o build e o deploy remotos sejam executados corretamente.

## Segurança e operação

O GitHub App da Cloudflare possui acesso somente ao repositório `annagodoy/ann4godoy-site`.

O projeto não utiliza secrets de aplicação. Arquivos locais como `.dev.vars` e o diretório `.wrangler/` não são versionados.

O Cloudflare Access permanece desativado porque o site é público.

## Quando reavaliar esta decisão

Esta decisão deve ser revisada se:

- o site precisar de SSR, backend ou funções de servidor;
- houver necessidade de migrar a infraestrutura para AWS;
- custos ou limites da Cloudflare se tornarem relevantes;
- o projeto exigir maior controle sobre o processo de publicação;
- for necessário impedir que um deploy aconteça sem uma aprovação adicional;
- a adoção de domínio próprio alterar os requisitos de hospedagem.
